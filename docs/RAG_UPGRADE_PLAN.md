# Memoria RAG 检索质量升级规划

> 制定：2026-09-28，基于 Context7 查得的 Chroma / LangChain 当前文档 + 代码实测探针
> 起点：145 passed；检索核心 `rag/retrieve.py` 49 行手写，保持「检索核心自己写」红线

---

## 1. 现状与问题（均经实测确认，非推测）

### 问题一 · 重排窗口 k=8 过窄（最影响召回）

`retrieve.py:39-40` 为 `k=8, top_n=4`：向量检索召回 8 个候选，关键词重排再从这 8 个里选 4 个。

**关键约束**：关键词重排只能重排**已进入候选池**的文档。真正相关的文档若排在向量
结果第 9 名之外，关键词分数再高也无用——重排被前置召回瓶颈架空。

行业常规做法是 first-stage 召回 50-100 再重排取 3-5。Chroma 官方文档亦指出
`ef_search` / `n_results` 过小会直接限制召回上限。

**注意**：这不是单纯的 bug。`top_n` 增大直接推高 LLM 的 token 成本，是需要权衡的取舍。

### 问题二 · 切分在句子中间硬切（实测确认）

`chunk_text` 是纯固定窗口（size=800, overlap=100），不识别标点与段落边界。探针输出：

```
块 #0 结尾: '...需要提前 30 天发起续费'
结尾断在句中: True
```

切出的块首尾都是半句，嵌入模型编码的是残缺语义，向量质量明显低于完整句。
**语义边界对齐是当前 RAG 文献共识度最高的低成本优化**。

### 问题三 · 中文分词产生跨词垃圾 token

实测 `_tokens("什么时候需要提前续费")`：

```
['么时', '什么', '候需', '前续', '提前', '时候', '续费', '要提', '需要']
```

`么时`/`候需`/`前续`/`要提` 是跨词边界的垃圾二元组，不携带语义却参与
`keyword_score` 的分母计算，稀释真实关键词权重。纯停用词 `的了是在` 同样产生 token。

### 问题四 · keyword_score 无 IDF 权重

实测：

```
相关     keyword_score = 0.4167
部分相关   keyword_score = 0.0000
完全无关   keyword_score = 0.0000
```

「部分相关」与「完全无关」同分。BM25 解决的正是此问题：常见词权重低、罕见词权重高。
这直接影响 feat-040 新增的 `_select_relevant()`——当时已撞见过「所有页面都有
0.2857 基线分」，用「页数 ≤ K 时不截断」绕过，**根因未解**。

### 问题五 · 每次查询都重新 embedding

`retrieve.py:43` 为 `embedder.embed([question])[0]`，无任何复用。多轮追问时
上一轮 query 向量已在 checkpoint 中却仍重发。注：feat-041 的 `cache_control`
只作用于 system prompt，不覆盖 query 向量本身。

### 问题六 · 无检索质量可观测性

全仓库无 `recall` / `precision` / `hit_rate` 任何字样。`citations_verified`
只检查回答是否标注引用，**不检查引用内容是否相关**——标了 `[1]` 但 `[1]`
不相关的答案会被判为「已溯源」。

### 问题七 · Chroma HNSW 配置形式已迁移

当前：`metadata={"hnsw:space": "cosine"}`
官方当前文档：`configuration={"hnsw": {"space": "cosine", "ef_construction": 200}}`

旧写法仍可用（非缺陷），但 `configuration` 形式才能调 `ef_construction` / `ef_search`
——后者正是控制召回质量与召回量的旋钮，与问题一直接相关。

## 3. 执行项

### feat-050 · 检索评测基线（先做，其余项的验证依据）

**理由**：没有评测就无法判断后续改动是变好还是变坏。必须先有尺子。

**方案**：新增 `tests/test_rag_eval.py`，用确定性语料（4 份主题互斥的文档）
构造 3 条可判定的查询，测量 recall@4 与首个正确块的排名。

**⚠ 方案修正（实测发现）**：初稿想用一个 "flat embedder"（所有文本返回相同向量）
来隔离关键词项的作用。**这个设计是错的**——向量相同时 `combined_score` 里的
`vsim = 1 - distance` 对所有候选都相等，最终排序退化为 `store.search` 的任意返回
顺序，重排根本没被测量到。实测证据：`苹果多少钱` 正确文档 kw=0.25 却排在
kw=0.0 的 `car` 之后。已改为用 `FakeEmbedder` 测真实混合管线的端到端效果。

**实测基线（feat-050 记录的当前水位）**：

| 查询 | 期望文档 | recall@4 | 首个正确块排名 |
|---|---|---|---|
| 苹果多少钱 | fruit | ✓ | 1 |
| 交通工具有哪些 | car | ✓ | 1 |
| 服务什么时候到期 | sub | ✓ | **2** |
| **合计** | | **3/3 (100%)** | MRR 0.83 |

**关键发现**：`服务什么时候到期` 排第 2 而非第 1。原因是「什么时候」被切成
`么时`/`什么`/`时候`，与语料中的「将于...到期」**字面零交集**，关键词项
kw=0.0 完全失效，该查询**全靠向量侧命中**。这直接印证了问题三（中文分词噪声）。

**⚠ 判断被后续实测推翻**：小语料（4 份文档）下 k 从 8 放宽到 30 无任何变化，
我据此一度下调了 feat-054 的优先级。**这是错的**——小语料里相关块本就在候选池内，
k 自然不是瓶颈。构造 41 份文档、目标埋在第 20 位的语料后：

| k | 是否召回「到期」 | 排名 |
|---|---|---|
| **8** | **否** | — |
| 15 | 是 | 3 |
| 30 | 是 | 3 |

`k=8` 时答案里**完全没有**「到期」相关内容。延迟实测（本地 Chroma 查询，
不含 embedding 网络往返）：k=8 → 2.35ms，k=15 → 3.34ms，k=30 → 5.89ms。
相对秒级的 LLM 往返，这个开销可忽略。**k 改为 30，feat-054 保留。**

**教训**：评测语料的规模决定了结论的适用范围。小语料上的"无变化"不等于
"无影响"。已由 `test_narrow_recall_window_finds_nothing` 锁定该失败模式。

**验收**：4 个测试通过，作为回归守卫（不硬编码为等值断言，基线数字记录在本文档）。

### feat-051 · 语义边界切分

**方案**：`chunk_text` 在标点/段落边界切，保留 overlap 语义。

关键约束：**`start` / `end` 偏移量是红线引用的定位依据**，
改为语义边界切分后偏移量必须仍精确指向原文位置。

**验收**：
- 块首尾落在标点/段落边界（探针断言 `断在句中: False`）
- 全部块 `text == source[start:end]` 恒等（偏移正确性，红线）
- overlap 不丢失内容
- 既有 `test_ingest_search_cites_source` 等全绿

**风险**：中。改动会影响所有既有 chunk 的边界，引用偏移是红线，必须有等价性测试。

### feat-052 · 中文分词去噪（范围经实测收窄）

**方案（修正后）**：CJK run 先按标点/子句边界切开，句内再取二元组；过滤纯停用词
run 产生的 token。

**⚠ 实测修正**：初稿期望「句内跨词碎片」（`候需`/`前续`/`要提`）也能消除。
**实测证明这在无词典前提下不可行**——`re.findall(r"\w+", "什么时候需要提前续费")`
返回单个 run，其二元组 `候需` 与真词 `提前` 在字符层面完全同构，无从区分。

`\w+` 本身**已按标点切分**，故「跨句碎片」（如 `费逾`）本就不存在。
经实测可解的只有：停用词 run 过滤（`的了是在` → 空集）。

**跨词碎片的真正解法是 feat-053 的 IDF**：df≈100% 的碎片（任何 chunk 都含）
权重趋近 0，而真词 `续费` 的 df 低、权重高。这是 BM25 的标准做法，
无需词典即可生效。故 feat-052 不再承诺消除跨词碎片。

**约束**：`keyword_score("苹果 价格", "苹果今日价格") == 1.0` 是既有精确断言，
改动不得破坏。

**验收**：
- 停用词串 `的了是在` 产生空 token 集
- 单字 CJK 查询（「书」）不被丢弃
- ASCII 路径完全不变
- 既有 keyword_score 精确断言与边界断言全绿

### feat-053 · keyword_score 加 IDF

**方案**：从向量库收集语料统计文档频率，为查询 token 计算权重
`idf = log(N / df)`，加权后求和而非纯命中计数。

**约束**：`keyword_score` 现有签名 `(query, text) -> float` 被
`wiki/ops.py _select_relevant` 与 `retrieve` 共用。加 IDF 需 df 统计，
**不得破坏现有两处调用点**。

**验收**：
- 罕见词命中的得分 > 常见词命中的得分（同长度查询下）
- 现有两处调用点无需改动即可受益，或改动后全绿

**风险**：中。`keyword_score` 是纯函数，加 IDF 会引入状态（df 表）。
**优先方案**：用可选参数传入 df 统计，缺省退化为当前行为，保持向后兼容。

### feat-054 · 扩大召回窗口 k

**方案**：`k` 从 8 提到 30（`top_n` 暂不变，等评测数据再定）。

**依赖**：feat-050 的基线。改完后 recall@4 应有可测量的提升。

**验收**：
- 用 feat-050 的评测集证明 recall@4 提升
- 既有 retrieve 测试全绿
- 记录延迟变化（候选池增大会增加 Chroma 查询耗时，但远小于 LLM 调用）

    ↓

## 5. 风险与红线

| 风险 | 缓解 |
|---|---|
| 改切分破坏引用偏移（红线） | 强制断言 `chunk.text == source[chunk.start:chunk.end]`，语义边界切分只是**选择切点**，不改变偏移语义 |
| 改分词破坏既有精确断言 | feat-052 验收要求既有 keyword_score 测试全绿 |
| IDF 引入状态，破坏纯函数 | 用可选参数，缺省退化为当前行为 |
| 扩 k 推高延迟 | 候选池只影响本地 Chroma 查询，量级远小于一次 LLM 往返 |
| `top_n` 增大推高 LLM token 成本 | **本轮不调 `top_n`**，等评测数据再决策 |

**红线复核**：本轮不触碰删除逻辑、raw/ 只读、邮件保护、LangGraph 编排。
引用溯源是唯一高风险项，已在 feat-051 验收中设强制断言。

### 两处方案被实测修正

1. **feat-050 的隔离方案错误**：用相同向量隔离关键词项是无效的——向量相同时
   `combined_score` 的向量项对所有候选相等，排序退化为 `store.search` 的任意顺序，
   根本没测到重排。改用 FakeEmbedder 测真实混合管线。
2. **feat-054 的优先级判断错误**：小语料上"k 无影响"的结论不适用于大语料。
   见 §3 feat-054 的对照表。

### 遗留未做（已评估）

- **query 向量缓存**：`retrieve` 每次都重新 embedding，多轮追问时上一轮 query
  向量已在 checkpoint 中却仍重发。取决于实际多轮使用频率，另议。
- **Chroma `configuration` 迁移**：`metadata={"hnsw:space"}` → 
  `configuration={"hnsw": {...}}` 可调 `ef_search`/`ef_construction`。
  旧写法仍可用，非缺陷。
- **嵌入/响应缓存**：当前无。
- **语义分词器**（jieba / 最大匹配）：`候需` 类碎片已被 IDF 压低，若实测仍不够
  再考虑，届时需重新讨论「检索核心自己写」的红线边界。
